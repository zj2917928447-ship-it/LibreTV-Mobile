# LibreTV Mobile 2.23.2 — GitHub Upstream Review

Review date: 2026-11-14
Working directory: E:\\Github\\电影\\LibreTV-Mobile

## Executive decision

Keep the official LibreTV 2.23.2 server/application architecture, preserve the mobile PWA work already in this worktree, take the upstream SSRF fixes, and upgrade only the compatible media dependencies. For Android, use a verified Trusted Web Activity generated by Google's Bubblewrap rather than replacing the server with a WebView/Capacitor fork.

### Security fixes retained

- #980: connection-layer private-network access is now the intersection of the caller's live-request intent and the deployment's explicit LIVE_ALLOW_PRIVATE=1 switch. The live URL validator alone cannot disable the connection-time DNS rebinding check.
- #984: protected requests use the dependency's own undici fetch implementation with its own Agent. This avoids passing an undici@6 dispatcher to a different runtime-bundled undici implementation (notably Node 26).
- CI tests Node 22, 24 and 26, and avoids using matrix context in workflow-level concurrency.

## Media stack review

| Component | Selected version | Decision |
| --- | ---: | --- |
| ArtPlayer | 5.4.0 | Keep current player; make the dependency range explicit at ^5.4.0 |

| mpegts.js | 1.8.2 | Keep; matches the latest stable release reviewed |

### Why hls.js 1.7.4

The official 1.7.4 release includes fixes around low-latency HLS part/fragment boundaries, playlist refresh, buffer handling, audio-track switching, subtitle parsing, and demux/timestamp handling.

The 1.6 → 1.7 migration guide says no public exports were removed and no application code changes are required for the upgrade. The worktree was already on 1.7.3, so the 1.7.4 patch update was lower risk than changing player architecture.

- Release: https://github.com/video-dev/hls.js/releases/tag/v1.7.4
- Migration guide: https://github.com/video-dev/hls.js/blob/v1.7.4/MIGRATING.md

### Why ArtPlayer is not replaced

ArtPlayer 5.4.0 is already installed in the worktree. Its release includes a Vite build refactor, a reset method, fullscreen behavior changes and player fixes. Replacing it with another player would introduce avoidable risk to the current fullscreen, skip-mark, subtitle, and recovery integrations. The current ArtPlayer integration is retained; physical-device playback remains a separate acceptance gate.

- https://github.com/zhw2590582/ArtPlayer/releases/tag/5.4.0

### Why mpegts.js is not replaced

mpegts.js 1.8.2 remains the latest stable release reviewed. It is already the installed version and is used for the HTTP-FLV path. No reason was found to replace it.

- https://github.com/xqq/mpegts.js/releases/tag/v1.8.2

## Public hosting review

### Selected: Render Node.js Web Service (free tier for initial personal deployment)

- Render officially supports full Next.js applications as Web Services, including server-side logic and API routes; this project is not suitable for GitHub Pages static hosting.
- The repository now includes `render.yaml`, `.node-version` and a cross-platform `scripts/start.mjs` launcher that reads the platform-injected `PORT` (local default 8080).
- The Blueprint uses Node 24.18.0, `npm ci && npm run build`, `npm start`, `/api/status` health checks, generated `PASSWORD` / `PROXY_SECRET`, `COOKIE_SECURE=true`, and `LIVE_ALLOW_PRIVATE=0`.
- Render Free is only a personal/test tier: idle services sleep after 15 minutes and need roughly one minute to wake; the workspace has 750 Free instance hours/month, local filesystem is ephemeral, and outbound bandwidth is limited. LibreTV stores history/settings client-side, so server-side persistent disk is not required. Streaming bandwidth can still exceed free allowances; no claim of unlimited free streaming is made.

Official references:
- https://render.com/docs/deploy-nextjs-app
- https://render.com/docs/free
- https://render.com/docs/blueprint-spec

### Why Cloudflare Workers was not selected for this stable release

- Cloudflare currently recommends vinext for new Next.js deployments; vinext is in beta and the official docs advise checking compatibility before migrating an existing production app.
- OpenNext supports App Router, Route Handlers, SSR and response streaming, but the current app's protected fetch path uses Node DNS resolution and an Undici Agent for DNS-rebinding protection. This runtime-specific security path must be adapted and tested before a Workers migration; do not simply deploy and silently weaken it.
- The existing quick-tunnel 404 was caused by loading the machine's default cloudflared config (which has a different hostname ingress and a final 404 rule). A separate no-credentials quick-tunnel config fixed routing and passed external HTTP 200 checks. Quick Tunnels remain temporary development URLs, not production hosting.

Official references:
- https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/
- https://developers.cloudflare.com/workers/framework-guides/web-apps/opennext/
- https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/

## Android packaging review

### Selected: Bubblewrap + Trusted Web Activity

- Bubblewrap CLI: 1.27.0, Apache-2.0
- Android Browser Helper: 2.7.4, Apache-2.0
- Bubblewrap wraps the already-hosted PWA as a verified Android Trusted Web Activity. It preserves the existing Next.js server routes, authentication, playback proxy and SSRF controls.
- A public HTTPS domain, stable Android application ID, signing key and matching /.well-known/assetlinks.json are required before an installable verified TWA can be built.

References:
- https://github.com/GoogleChromeLabs/bubblewrap
- https://github.com/GoogleChromeLabs/bubblewrap/releases/tag/v1.27.0
- https://github.com/GoogleChrome/android-browser-helper/releases/tag/android-browser-helper-2.7.4
- Detailed steps: ANDROID-TWA-SETUP.md

### Rejected as the production base

- https://github.com/pwa-builder/pwabuilder-android-twa — archived; do not build a new app on the archived repository. PWABuilder's current TWA packaging route uses Bubblewrap.
- https://github.com/065021/libretv-mobile — the reviewed fork is based on LibreTV 2.19.0 and uses app-only shims that bypass authentication/SSRF checks. It is useful as a research reference, not as a safe direct upgrade for the 2.23.2 server architecture.
- Capacitor/WebView rewrite — not selected because it changes the server execution model and creates a second place to maintain route, media-stream and security behavior.

## Framework version decision

- Current locked Next.js: 15.5.29 (updated from 15.5.26 within the Next.js 15 line to clear the reported advisories).
- Latest upstream Next.js release reviewed: 16.4.6 (2026-11-09).
- We deliberately did not perform a major Next.js 15 → 16 migration in this release. The official LibreTV 2.23.2 baseline remains on Next.js 15; a major upgrade changes build/runtime defaults and deserves a separate compatibility branch with production playback and deployment tests.
- 15.5.29 is above the patched floor noted in the security guidance for the 2025 React2Shell advisory and also clears the 15.5.27-or-earlier advisories reported by the current npm audit. This is not a claim that every future advisory is covered; keep running npm audit and update promptly.

Reference: https://github.com/vercel/next.js/releases/tag/v16.4.6

## Additional hardening in this worktree

- Touch input detection now uses any-pointer: coarse so a touchscreen remains recognized when a mouse/trackpad is also connected.
- Malformed percent-encoded session cookies now fail closed as unauthenticated instead of throwing URIError and turning guarded API requests into 500 responses.
- Added baseline response headers: X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Permissions-Policy; removed the X-Powered-By header.
- No HSTS header is hard-coded because deployments may run over HTTP behind different reverse-proxy configurations.
- No broad CSP is added in this release because the app uses Next.js inline bootstrap scripts and dynamic media sources. A nonce-based CSP should be introduced only after validating all playback/provider origins and the production edge setup.
